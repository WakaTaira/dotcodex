# 作業依頼書フォーマット

次の例を土台に、既存の設計書と文書規約を優先する。短い依頼では節を統合し、意味のない空欄を増やさない。目的・対象・制約・完了の判定は読み取れる状態にする。

```markdown
# 作業依頼: <タイトル>

## 目的と現状

<何が起きており、誰が何に困っているか。観測事実と期待を区別する>

## 変更内容

<変更後の挙動と、必要な設計判断。実装方法を固定するのは理由がある箇所だけ>

## 対象と制約

<変更する範囲、互換性、保護対象、担当を分ける場合の書き込み範囲>

## 完了条件

<検証コマンドと期待結果。手動確認には操作と観測点を添える>

## 受け入れ条件

- AC-1: Given <前提> / When <操作> / Then <期待する挙動>

## 未決定事項

<結果や範囲に影響する判断、仮定、その確認方法。なければ省略する>
```

受け入れ条件は利用者や呼び出し元から観測できる挙動を表し、内部の関数名やファイルの存在だけを成功としない。条件 ID を使うと、テストを分割・パラメータ化しても対応を追える。

対象と制約は変更の境界、完了条件は変更全体の検証、受け入れ条件は挙動の契約を示す。手動確認の条件にも操作と期待結果を記し、単に「実機で確認」とは書かない。

将来の読者が迷う設計判断には、判断日、採用案、理由、退けた代替案を添える。小さな実装上の選択をすべて設計書へ列挙する必要はない。
