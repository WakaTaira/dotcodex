# relay

設計合意済みタスクを、Codex を主セッションとして完了まで運ぶ。メインセッションは設計判断・実装・監査を担い、必要な箇所だけを Luna のサブエージェントまたは Fable MCP へ委譲する。

## 構成の原則

- **メインセッション（Sol）**: ユーザーとの合意、実装、検証結果の統合、最終監査を担当する。
- **Luna**: 実装を別レーンへ切り出す必要がある大規模・独立・反復的な作業だけを担当する。
- **Fable**: 個人層の MCP ブリッジ経由で読み取り専用レビューを担当する。

小さく局所的な変更はメインセッションが直接実装する。実装担当を常に別エージェントに分けることは、この構成の要件ではない。

Claude 側から Codex を呼ぶ旧 `relay-codex` ラッパーは主経路にしない。Codex が主セッションであるため、Codex から直接 Luna を起動し、レビュー時だけ Fable MCP を呼び出す。

## 開始条件

1. `brief-me` または `grill-me` で目的と設計が合意済みである。
2. タスクに **目的・対象・制約・完了条件** の 4 項目がある。
3. 受け入れ条件がある場合は、実装前に `gauntlet` でテスト化している。
4. 対象リポジトリの `AGENTS.md`、既存の検証コマンド、現在の差分を確認している。

設計判断が残っている場合は実装を始めず、`grill-me` に戻る。

## 委譲の判断

次のいずれかに該当するときだけサブエージェントを使う。

- 独立した調査・検証を並列に走らせると、メインのコンテキストを節約できる。
- 変更が大きく、対象ファイル・制約・完了条件を完全に切り出せる。
- Luna に固定した実装レーンを明示的に使う必要がある。

それ以外はメインセッションで直接実装する。

| 役割 | Codex エージェント | 用途 |
|---|---|---|
| 調査 | `relay_investigator` | 読み取り専用のコードパス・依存関係調査 |
| 実装（高難度） | `relay_implementer` | 複数ファイル、境界条件、複雑なデバッグ |
| 実装（標準） | `relay_implementer_std` | 仕様確定済みの通常実装 |
| 検証 | `relay_verifier` | テスト・ビルド・lint の実行。修正はしない |
| 機械作業 | `relay_mechanic` | 判断を含まない探索・定型置換 |
| Fable レビュー | `relay_fable_reviewer` または MCP 直接呼び出し | Claude Code の Fable による独立レビュー |
| Fable 不在時 | `relay_reviewer` | Codex 内の読み取り専用フォールバック |

## 実行手順

### Step 1: 仕様を固定する

サブエージェントを使う場合は、次の表を会話に出してから起動する。直接実装の場合も、メインの作業メモとして同じ 4 項目を確認する。

| # | タスク | 依存 | 担当 | 完了条件 |
|---|---|---|---|---|
| 1 | （何をするか） | なし | メイン / `relay_investigator` | （機械的に判定できる条件） |
| 2 | （何をするか） | #1 | メイン / `relay_implementer*` | （同上） |
| 3 | （何をするか） | #2 | `relay_verifier` | （同上） |
| 4 | （何をするか） | #2, #3 | Fable レビュー | 指摘なし、または対応済み |

依存関係のない調査・検証は並列に起動してよい。同じファイルを触る書き込みタスクは並列にしない。

### Step 2: 実装する

- 指定された対象ファイル以外を変更しない。
- 仕様にない設計判断が必要になったら停止し、未確定事項として報告する。
- コメントは日本語・フォーマルな文体とし、コードから読み取れない制約だけを書く。
- 実装担当を使う場合、メインは同じ変更を重複して編集しない。
- 完了条件に書かれた検証コマンドを実行する。

レビュー指摘への修正を再委譲するときは、指摘を確定事項として仕様に転記する。実装側に妥当性の再判定をさせない。

### Step 3: 検証する

完了条件に書かれたコマンドを優先する。追加の検証を行った場合は理由を残す。サブエージェントの成功報告だけでは完了とせず、メインが結果を再実行するか実行ログを確認する。

### Step 4: Fable でレビューする

コード変更を含むタスクでは、仕様と検証結果をそろえてから Fable レビューを依頼する。レビュー軸は混ぜない。

- **仕様軸**: 合意した目的・境界・完了条件との一致、欠落、スコープ逸脱。
- **規約軸**: リポジトリ規約、セキュリティ、保守性、実在するコードスメル。

可能なら 2 軸を別々に Fable へ渡す。MCP サーバー名は `claude_fable_reviewer`、ツール名は `review_with_fable` を標準とする。依頼には `cwd`、目的、対象、制約、完了条件、レビュー軸を含める。

Fable MCP が利用できない場合は、未認証・Claude CLI 不在・モデル不在・タイムアウトなどの原因を記録し、Fable がレビューしたとは報告しない。ユーザーが許容する場合だけ `relay_reviewer` をフォールバックとして使う。

## Fable MCP の安全境界

個人層リポジトリの MCP ブリッジは、公式 Claude Code CLI のログイン済みセッションを利用して `claude -p --model fable` を起動する。Codex から Anthropic API を直接呼ばない。レビューは `plan` モードと読み取り用ツールだけで実行し、編集ツールを渡さない。

レビュー依頼に秘密情報・トークン・認証ファイルを含めない。差分を渡す必要がある場合も、対象リポジトリを Fable が読めるよう `cwd` と指示を渡す。

## 監査

完了報告の前に、メインセッションは次を確認する。

- 対象外ファイルに変更がない。
- 受け入れ条件と検証結果が対応している。
- Fable の各指摘に対して、修正・棄却・未解決のいずれかが記録されている。
- Fable を呼べなかった場合、その事実と原因が明記されている。
- 既存の Claude 側資産やユーザーの未関連変更を上書きしていない。

## 報告形式

```text
## 結果: 完了 / 部分完了 / 失敗
## 変更ファイル: （フルパスの一覧）
## 実行コマンドと結果: （実際の出力）
## レビュー: Fable / フォールバック / 未実施（理由）
## 判断したこと: （指示になかった判断。なければ「なし」）
## 未解決・懸念: （なければ「なし」）
```
