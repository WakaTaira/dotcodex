# relay

設計合意済みタスクを、Codex のメインセッションを中心に実装・検証・レビューまで運ぶ。通常の作業は Codex モデルで完結し、判断が難しい箇所だけ Fable 5.1 に相談する。

## 構成の原則

- **メインセッション**: 現在選択されている Codex モデルで、ユーザーとの合意、実装、検証結果の統合、指摘の採否、最終監査を担当する。
- **Codex サブエージェント**: 独立した調査・実装・テスト作成・検証・レビューを担当する。実装の既定は Luna、難所はメインまたは Sol が担う。
- **Fable 5.1**: 個人層の MCP ブリッジ経由で、行き詰まり、設計案の比較、指摘への見解相違を読み取り専用で検討する相談役である。実装担当や必須の承認者にはしない。

小さく局所的な変更はメインセッションが直接実装する。実装担当を常に別エージェントに分けることは、この構成の要件ではない。

指定した Codex モデルが利用できない場合は、原因と途中差分を確認し、利用可能な Codex モデルへ作業を引き継ぐ。書き込み担当の停止を確認してから引き継ぎ、同じ障害への再試行を繰り返さない。Claude への実装フォールバックは設けない。

Codex 自身が実装するため、`codex mcp-server` や Claude 側の `relay-codex` を経由する必要はない。サブエージェントには Codex ネイティブの起動・継続機能を使う。Fable への相談時だけ [相談手順](references/fable-consultation.md) を読む。全エージェント定義や補助資料を開始時に一括で読み込まない。

## 開始条件

1. 会話または `brief-me` / `grill-me` の設計書で目的と設計が合意済みである。小さく自明な変更に設計書の新設は求めない。
2. タスクに **目的・対象・制約・完了条件** の 4 項目がある。
3. 受け入れ条件がある場合は、実装前に `gauntlet` でテスト化している。
4. 対象リポジトリの `AGENTS.md`、既存の検証コマンド、現在の差分を確認している。

既存の合意から決められる実装上の選択はメインが解決する。目的・外部仕様・対象範囲を変える判断だけをユーザーへ戻し、独立して進められる作業は続ける。

## 委譲の判断

次のいずれかに該当するときだけサブエージェントを使う。

- 独立した調査・検証を並列に走らせると、メインのコンテキストを節約できる。
- 変更が大きく、対象ファイル・制約・完了条件を完全に切り出せる。
- 受け入れテストの作成者と実装者を、別スレッドと排他的な変更対象で分離する。

それ以外はメインセッションで直接実装する。

| 役割 | Codex エージェント | 用途 |
|---|---|---|
| 調査 | `relay_investigator` | 読み取り専用のコードパス・依存関係調査 |
| 実装（高難度） | `relay_implementer` | Luna max。複数ファイル、境界条件、複雑なデバッグ |
| 実装（標準） | `relay_implementer_std` | Luna low。既存パターンが確立した実装 |
| 受け入れテスト作成 | `relay_acceptance_writer` | Luna max。`gauntlet` の条件を外部挙動のテストへ変換 |
| 検証 | `relay_verifier` | テスト・ビルド・lint の実行。修正はしない |
| 機械作業 | `relay_mechanic` | 判断を含まない探索・定型置換 |
| 通常レビュー | `relay_reviewer` | Codex による読み取り専用レビュー |
| 難所の相談 | Fable MCP 直接 / `relay_fable_advisor` | Fable 5.1 による仮説・代替案・反証の検討 |

カスタム役割を指定できない環境では、必要な役割の TOML だけを読み、役割指示とモデル・effort をネイティブの起動引数へ渡す。モデルを明示する場合は全会話の fork を避け、対象・仕様・参照パスに絞って渡す。モデルや権限を指定できない場合は継承する実際の設定を明記し、指定どおりに動いたと報告しない。Luna max で不足する実装や新規テストハーネスは、メインが担当するか Sol high を明示指定する。固定モデルの役割定義が起動引数より優先する環境では、その役割を選ばずに起動する。

## 実行手順

### Step 1: 仕様を固定する

サブエージェントを使う場合は、次の表を会話に出してから起動する。直接実装の場合も、メインの作業メモとして同じ 4 項目を確認する。

| # | タスク | 依存 | 担当 | 完了条件 |
|---|---|---|---|---|
| 1 | （何をするか） | なし | メイン / `relay_investigator` | （機械的に判定できる条件） |
| 2 | （何をするか） | #1 | メイン / `relay_implementer*` | （同上） |
| 3 | （何をするか） | #2 | `relay_verifier` | （同上） |
| 4 | （何をするか） | #2, #3 | メイン / `relay_reviewer` | 指摘なし、または採否と対応を記録 |

依存関係のない調査・検証は並列に起動してよい。同じファイルを触る書き込みタスクは並列にしない。

委譲先には目的・対象・制約・完了条件に加え、作業ルート、参照すべき設計書・規約のパス、実行コマンドを渡す。参照資料は担当が必要な箇所を読み、長い全文や無関係な会話を中継しない。応答は変更ファイル、実行結果、未確定事項に絞る。継続や修正は同じエージェントへ渡し、同じ作業を別スレッドに重複起動しない。

### Step 2: 実装する

- 指定された対象ファイル以外を変更しない。
- `gauntlet` が固定した受け入れテスト・fixture・ハーネス設定を変更しない。配置名を決め打ちせず、引き継がれた実際の保護対象を使う。
- 仕様を変える判断が必要になったら該当箇所を保留し、実装可能な範囲と未確定事項を報告する。
- コメントは日本語・フォーマルな文体とし、コードから読み取れない制約だけを書く。
- 実装担当を使う場合、メインは同じ変更を重複して編集しない。
- 完了条件に書かれた検証コマンドを実行する。

レビューや相談の指摘はメインが事実と仕様に照らして採否を決める。採用した修正だけを確定事項として再委譲し、衝突する制約があれば修正担当に事実を返させる。受け入れテスト自体の誤りは `gauntlet` の作成担当へ戻し、期待結果を弱めて green にしない。

### Step 3: 検証する

完了条件に書かれたコマンドを優先する。追加の検証を行った場合は理由を残す。サブエージェントの成功報告だけでは完了とせず、メインが結果を再実行するか実行ログを確認する。

### Step 4: Codex でレビューする

仕様と検証結果をそろえて、メインまたは `relay_reviewer` が差分をレビューする。レビュー軸は混ぜない。

- **仕様軸**: 合意した目的・境界・完了条件との一致、欠落、スコープ逸脱。
- **規約軸**: リポジトリ規約、セキュリティ、保守性、実在するコードスメル。

規約のうち機械判定できるものは lint / format に任せる。受け入れテストの green は対応する条件の証拠であり、設計書の欠落や手動確認まで保証するものではない。

失敗原因を絞れない、案の比較が難しい、レビュー指摘の妥当性で判断が割れる場合は [Fable 相談手順](references/fable-consultation.md) を使う。相談の要否と最終判断はメインが持つ。

## 監査

完了報告の前に、メインセッションは次を確認する。

- 対象外ファイルに変更がない。
- 受け入れ条件と検証結果が対応している。
- レビューと相談の各指摘に対して、修正・棄却・未解決のいずれかが記録されている。
- Fable への相談を試みて失敗した場合、その事実と原因が明記されている。相談不要の作業は通常どおり完了できる。
- 既存の Claude 側資産やユーザーの未関連変更を上書きしていない。

## 報告形式

```text
## 結果: 完了 / 部分完了 / 失敗
## 変更ファイル: （フルパスの一覧）
## 実行コマンドと結果: （実際の出力）
## レビュー: Codex（担当・確認範囲・指摘の採否）
## 相談: Fable 5.1 / 不要 / 失敗（原因）
## 判断したこと: （指示になかった判断。なければ「なし」）
## 未解決・懸念: （なければ「なし」）
```
