# relay

メインセッションが設計判断、実装、検証結果の統合、レビュー指摘の採否を担当する。通常の作業は Codex モデルで完結し、判断が難しい箇所だけ Fable 5.1 に相談する。Astra を含む、ユーザーが現在選択している Codex モデルを使い、スキルからメインのモデルを変更しない。

## 着手と進行

会話・設計書から目的、対象、制約、完了条件を把握し、対象の規約と現在の差分を確認する。この情報がそろっていれば、定型表への転記や設計書の新設、再承認を着手条件にしない。レビューのみ、設計のみなどの依頼範囲は守る。

目的・外部仕様・対象範囲に影響する未決事項はユーザーへ戻す。既存の合意とコードから決められる実装上の選択はメインが解決し、未決事項から独立した作業は続ける。

実装前に独立した受け入れ契約を固定するタスクでは `gauntlet` を使う。小さな文書・設定変更に新しい受け入れハーネスを一律に求めず、完了条件に合う既存テスト・静的検査・実物確認を選ぶ。

## 委譲

メインのコンテキスト消費と、委譲を含む総作業量の両方を抑える。仕様を切り出せる実装や大量の資料を読む調査は適切な軽量モデルへ渡し、メインは重要な判断と統合に集中する。小さく局所的な変更は、引き継ぎのほうが高くつくため直接実装する。並列化、独立検証、作成者の分離に具体的な利益がない多段委譲や担当の増設は避ける。

| 役割 | 担当 |
|---|---|
| 独立した調査 | `relay_investigator` |
| 仕様確定済みの実装 | `relay_implementer` / `relay_implementer_std` |
| 受け入れテスト作成 | `relay_acceptance_writer` |
| コマンド実行と証拠確認 | `relay_verifier` |
| 判断を含まない定型作業 | `relay_mechanic` |
| 読み取り専用レビュー | `relay_reviewer` |

委譲先には目的・対象・制約・完了条件、作業ルート、必要な参照パスと検証コマンドを渡す。担当が必要箇所だけ読み、無関係な会話や全資料を中継しない。応答は変更、実行結果、判断が必要な点を中心にし、根拠のファイル位置と詳細ログの参照先を添える。メインはその要点と必要な証拠を確認し、担当が読んだ資料全体を読み直さない。矛盾、重大なリスク、証拠不足がある箇所だけ掘り下げる。継続や修正は同じ担当へ戻し、同じ作業を重複起動しない。

Codex ネイティブの起動・継続機能を使う。`codex mcp-server` や Claude 側の実装ラッパーを経由しない。カスタム役割やモデルの指定方法が必要な場合だけ [起動と引き継ぎ](references/delegation.md) を読む。分離不要の難所はメインが扱い、Luna へ渡すためだけに設計を過剰分割しない。

## 変更の境界

実装担当は指定対象だけを変更する。同じファイルを触る書き込みタスクは同時実行せず、メインも委譲済みの変更を重複編集しない。モデルが利用できなければ原因と途中差分を確認し、書き込み担当の停止後に利用可能な Codex モデルへ引き継ぐ。Claude への実装フォールバックは設けない。

`gauntlet` が固定したテスト・fixture・ハーネス設定は実装担当の変更禁止対象である。配置名を決め打ちせず、引き継がれた実際のパスと基準差分で監査する。テストが誤っている場合は条件文・観測結果・修正理由を作成担当へ返す。対象の実装と検証を止め、`gauntlet` の修正・独立検証・基準更新後に再開する。期待結果を弱めて green にしない。

レビューや相談の指摘はメインが事実と仕様に照らして採否を決める。新しい製品仕様を伴う指摘は実装担当へ確定事項として渡さず、必要な合意を取る。

## 検証とレビュー

完了条件のコマンドを優先し、変更の失敗経路と影響範囲に応じて検証を追加する。小さな変更にも同じ全件検証を機械的に課さない。委譲先の成功という結論だけでは完了とせず、対象リビジョン・コマンド・実際の出力を確認する。ログが現在の差分を検証しているなら、安心のためだけに同じ検査をやり直さない。

メインまたは `relay_reviewer` が、合意した挙動、回帰、安全性、テスト不足をレビューする。機械判定できる規約は lint / format に任せる。受け入れテストの green が保証するのは対応する条件であり、仕様の欠落や未実施の手動確認まで成功扱いしない。

失敗原因を絞れない、設計案の比較が難しい、指摘の妥当性で判断が割れる場合は [Fable 相談手順](references/fable-consultation.md) を使う。Fable 5.1 は読み取り専用の相談役で、必須の承認者ではない。相談不要なら通常どおり完了し、試みて失敗した場合は原因と残る不確実性を明記する。

## 完了報告

結果と変更理由を先に示し、実行した検証コマンドと実際の出力、レビューの要点、未解決事項を必要な分だけ添える。固定の節数や「なし」の列挙は求めない。

報告前に対象外変更と保護対象の差分を確認する。既存のユーザー変更を自分の成果に含めず、指摘は修正・棄却・未解決を区別する。未実施の検証や未解決の完了条件があれば、その範囲を明示する。
