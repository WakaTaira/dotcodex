# gauntlet

合意済みの外部挙動をテストへ変換し、作成担当とは別の担当が条件との対応と失敗理由を確認する。green はテスト化した条件の証拠であり、仕様の欠落や手動確認まで保証するものではない。

## 条件とテストの対応

会話または設計書から条件を読む。Given / When / Then の形式でなくても、前提・操作・期待結果が明確なら使える。既存の合意から一義に決まる内容は補い、新しい期待挙動や範囲を加える場合だけ確認する。

プロジェクトの既存フレームワークと配置規約を優先する。規約がなければ `tests/acceptance/` を候補にし、既存の実行環境に合う最小のハーネスを選ぶ。Given / When / Then の表記だけのために Gherkin ランナーを追加しない。

条件 ID とテスト名・コメントなどで対応を追跡可能にする。全条件をカバーすれば、パラメータ化や複数ケースへの分割を許容し、1 条件 1 関数や条件全文の重複転記を要求しない。機械判定できない条件は、その理由と手動確認の手順・期待結果をメインが確認する。

## 作成者の分離

`relay_acceptance_writer` を Codex の別スレッドで起動する。目的、合意済み条件、作業ルート、参照パス、実行コマンドを渡し、変更可能な新規テスト・fixture・ハーネス設定を列挙する。実装コードと無関係な既存テストは変更させない。

必要資料は担当が該当箇所だけ読む。モデル・effort の調整やカスタム役割を指定できない環境では、`relay` の [起動と引き継ぎ](../relay/references/delegation.md) に従い、作成者と実装者の境界を保つ。Claude / Fable にはテストを書かせない。

サブエージェント自体が使えない場合はメインがテスト作成と実装を別フェーズに分け、固定時の差分を記録する。別スレッドで分離したとは報告しない。

作成者は実装内部の構造を先取りせず、外部挙動を検証する。`skip` / `xfail` / 常に失敗する assert で red を作らない。

## 実行結果と固定

メインまたは別の `relay_verifier` がコマンドを独立に実行し、終了コード、対象ケース、失敗理由を確認する。

- **red**: 未実装の対象挙動が原因で落ちる。依存不足、構文エラー、未収集などはハーネスの問題として作成担当へ戻す。
- **既存 green**: 既存挙動ですでに満たす条件は根拠と検証範囲を記録し、無理に落とさない。
- **未検証**: 未実装なのに通るテストは条件と観測結果を作成担当へ返し、実行経路とアサーションを調べる。裏付けを得られなければ未検証のまま残す。
- **手動確認**: 自動化できない条件に具体的な手順と期待結果を割り当てる。割り当てただけで確認済みにはしない。

検証済みのテスト・fixture・ハーネス設定を保護対象として固定し、実際のパスと基準差分を記録する。全条件に対応先があっても、実行結果の裏付け前に完了とはしない。

## 固定後の訂正

テストの誤りはメインが根拠を確認し、条件文・観測結果・修正理由・修正対象を作成担当へ渡す。明示した保護対象だけの差し戻しであり、無関係な既存テストの変更許可ではない。仕様そのものを変える場合はユーザーと合意し直す。

差し戻し中は対象の実装担当と検証コマンドを停止する。修正後にメインまたは別の検証担当が再実行し、条件との対応を確認して基準差分を更新する。新しい基準と検証結果を実装担当へ渡してから再開する。期待挙動や検証範囲を弱めて green にしない。

## 引き継ぎ

条件とテストの対応、red / 既存 green / 手動確認 / 未検証、実行コマンドと実際の出力を返す。`relay` へは保護対象の実パスと基準差分、完了条件を判定するコマンドと期待結果、残る確認事項を渡す。

パスの変更禁止は指示と差分監査で守る運用上の境界であり、`workspace-write` 自体がファイル単位で強制する制限ではない。
