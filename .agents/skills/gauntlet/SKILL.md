# gauntlet

設計書の受け入れ条件を、実装より先に実行できる受け入れテストへ変換する。Codex の作成担当が外部挙動をテストし、メインが条件との対応と失敗理由を裏取りする。green はテスト化した条件の証拠であり、仕様の欠落や手動確認まで保証するものではない。

## 方式

Gherkin ランナー（cucumber 系）は使わない。Given / When / Then の構造だけを借り、プロジェクトの既存テストフレームワークで書く。step definition の維持コストを払わない。

- **配置**: `tests/acceptance/`（プロジェクトに既存のテスト配置規約があればそれに従う）
- **対応**: 受け入れ条件 1 項目 = テスト 1 本。テスト名とコメントに Given / When / Then を 1:1 で写し、設計書と突き合わせ可能に保つ
- **フレームワーク既定**（プロジェクトに既存があればそちらを優先）: Python = pytest / JS・TS = vitest / Rust = cargo test / シェル・CLI = bats / ブラウザ E2E = @playwright/test（NixOS では nix 管理の PLAYWRIGHT_BROWSERS_PATH 前提。npm 側の playwright は nixpkgs の driver と同系列のバージョンにする）/ TUI = bats + tmux（send-keys / capture-pane）
- **書き手**: `relay_acceptance_writer`（Luna max）を別スレッドで起動する。メインは仕様の転記、対象の固定、結果の裏取りを担い、実装担当へテスト作成を兼務させない。

## 実行手順

### Step 1: 入力を読む

設計書または会話で合意済みの受け入れ条件を読む。条件が無い場合は完了条件から Given / When / Then を起こす。既存の合意から一義に決まる内容はそのまま使い、新しい期待挙動や範囲を加える場合だけユーザーに確認する。

### Step 2: Codex の作成担当へ渡す

Codex ネイティブのサブエージェントへ、次の 4 項目と作業ルート・参照パスを渡す。Claude 側の実装ラッパーや Codex MCP を再起動する必要はない。

| 項目 | 渡す内容 |
|---|---|
| 目的 | 設計書名と、実装前の受け入れテスト作成であること |
| 対象 | 新しい受け入れテストの実際の配置先。fixture・ハーネス設定を追加する場合はそのファイルも列挙する。実装コード・既存テストへの変更は禁止 |
| 制約 | 合意済み条件の全文、既存の配置・フレームワーク規約、1 条件 1 テスト、外部挙動の検証、人工的な失敗の禁止 |
| 完了条件 | 全条件をテストまたは機械判定不能へ対応付け、指定コマンドと実際の出力、各失敗の原因を報告する |

必要な資料は作成担当が該当箇所だけ読む。既存パターンへの単純追加なら Luna low、新規ハーネスなら Sol high を明示して別スレッドを起動する。カスタム役割がモデル・effort を固定する環境では `relay_acceptance_writer` を選ばず、その TOML の作成者指示を渡して指定する。全会話を fork せず、仕様と参照先に絞る。

作成者は `skip` / `xfail` / 常に失敗する assert で red を作らず、実装内部の構造を先取りしない。画面の印象や操作感など機械判定不能な項目は理由を返す。メインが妥当性を確認し、手動確認の手順と期待結果へ割り当てる。全条件に対応先があっても、red の裏取り前には完了としない。

指定モデルが利用できなければ、失敗した担当の停止と途中差分を確認し、作成者の境界を維持した別の Codex スレッドへ引き継ぐ。Claude / Fable にはテストを書かせない。サブエージェント自体が利用できない場合はメインがテスト作成と実装を別フェーズに分け、固定時の差分を記録して検証する。別スレッドで分離したとは報告しない。

### Step 3: red を確認する

メインまたは別の `relay_verifier` がコマンドを再実行し、成功報告だけで判定しない。終了コード、対象ケース、失敗理由を確認する。依存関係不足、構文エラー、テストが収集されない状態は未実装の証拠にはならず、ハーネスの問題として作成担当へ戻す。

変更対象の挙動が未実装のため落ちることを確認する。既存挙動ですでに通る項目は、その根拠と検証範囲を記録し、無理に落とさない。未実装の条件なのに通るテストは同じ担当へ条件名と観測結果を返し、アサーションや実行経路を確認させる。修正しても裏付けられなければ未検証として残し、green の条件を捏造しない。

検証済みのテスト・fixture・ハーネス設定を保護対象として固定し、その時点の差分を記録する。誤りが判明したときはメインが根拠を確認し、条件文・観測結果・修正理由と修正対象を作成担当へ渡す。これは固定済みテストを修正する明示的な差し戻しであり、無関係な既存テストの変更許可にはならない。仕様そのものを変える場合はユーザーと合意し直す。

差し戻し中は対象の実装担当と検証コマンドを停止する。修正後にメインまたは別の検証担当が再実行し、条件との対応を確認して保護対象の基準差分を更新する。新しい基準と検証結果を実装担当へ渡してから再開する。

### Step 4: relay へ渡す形で報告する

条件とテストの対応、red / 既存 green / 手動確認 / 未検証、実行コマンドと実際の出力を報告する。`relay` へは次を渡す。

- 完了条件: 実際のテストパスと実行コマンド、その期待結果。
- 変更禁止対象: 固定したテスト・fixture・ハーネス設定の実際のパス。`tests/acceptance/` 以外の配置にも適用する。
- 手動確認と未検証の項目、その理由と次の確認。

同じモデルでも別スレッド・別仕様・排他的な変更対象で役割を分離する。パスの変更禁止は指示と差分監査で確認する運用上の境界であり、`workspace-write` 自体がファイル単位で強制する制限ではない。
