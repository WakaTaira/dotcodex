# Pull Request の作成・更新

PR の説明は、問題・変更後の挙動・判断理由をレビュアーへ伝える。将来の読者が変更の必要性を理解するための記録でもある。調査と共通原則の出典は [PROVENANCE.md](PROVENANCE.md) にある。

## レビューの前提

対象リポジトリの貢献ガイドと PR テンプレートを優先する。セッションで確認済みの情報は再利用し、文体や記入方法が不明なときに直近のマージ済み PR を参照する。テンプレートの必須項目、HTML コメント、該当なし欄の扱いは、その指示と慣習に従う。チェックリストは実際に確認した項目だけチェックする。

対象リポジトリ、既存 PR の有無、意図する base と head を特定し、その base に対する diff 本体と関連する議論・検証結果を読む。PR の取得失敗には認証や通信の原因もあるため、PR が存在しない場合と区別する。エラーを隠して `main` に置き換えない。新規 PR の対象ブランチは依頼とリポジトリの情報から定める。対象がなお曖昧なら、判明している情報で文案を整え、投稿前に曖昧さを解消する。

不慣れな外部リポジトリでは、過去の議論が提案の範囲や理由に関わる場合に関連 Issue・PR を調べ、今回の提案との関係を説明する。PR 文面の作成だけを理由に、オプトアウト用の設定などを実装へ追加しない。

## 説明の組み立て

説明量は変更のリスクとレビューに必要な判断で決める。局所的な修正なら、問題と結果の短い説明に必要な検証を添えるだけでよい。互換性を変える 1 行には移行説明が必要になり、生成ファイルの大量更新には詳しい本文が不要な場合もある。

- **タイトル**は対象と変更の挙動が伝わる常体・体言止めを基本とし、prefix はリポジトリの慣習に合わせる。
- **冒頭**で具体的な問題や目的と変更後の挙動を伝える。理解に役立つ場合は、発生条件と変更前後の例を添える。
- **設計と影響**では重要な選択、互換性、トレードオフを説明する。見送った案や制約はレビュー判断に関わる場合に記載する。上流バグの暫定回避には、上流 Issue・PR へのリンクと具体的な撤去条件を添える。
- **検証**は証拠から確認できる結果と重要な未確認事項を書く。性能などの測定結果には実測値を使い、根拠と条件を示す。現在の変更にも適用できる検証結果は再利用し、差分や証拠の不足が再実行を必要とする場合だけ追加確認する。
- **読み方の補助**は理解に役立つ場合に選ぶ。入口となるファイル、関係図、実行結果、スクリーンショットを使い、読む順序やファイル間の関係が分かりにくい場合には表を添える。

本文の文体は対象リポジトリに合わせる。慣習が不明なら簡潔なです・ます調を基本とし、箇条書きには体言止めも使える。過度な挨拶や定型的な判断依頼は加えない。文体・テンプレート運用の参考が必要なら [references/examples.md](references/examples.md) を読む。実例集の統計や個別事例は、対象リポジトリの指示に優先する規則ではない。

変更後の挙動は diff にも現れていてよい。ファイルごとの機械的な読み上げや作業経過を省き、何がどう変わり、なぜ必要なのかを残す。テンプレートがなければ、`概要`、`背景`、`影響範囲`、`テスト内容`、`関連 Issue` などから読者に役立つ見出しを選ぶ。関連情報がない見出しを埋めるために説明を増やさない。

長いログなどの補足は `<details>` に置けるが、変更理由と重要な制約は展開せず読める位置に残す。詳細をリンク先に任せる場合も、変更を理解するための前提は本文に残す。

## 既存 PR の更新

意図する base に対するブランチの現在の姿を説明する。古くなった範囲の説明を書き換え、変更履歴を追記する構成を避ける。関連する Issue、未解決のレビュー判断、有効な検証根拠は保持する。変更で適用できなくなった検証結果は実施時点を明らかにし、現在の差分の根拠として扱わない。

Issue を解決する意図がある場合だけ `fixes` や `resolves` を使う。参照のみなら `ref: #123` などとし、他リポジトリには `owner/repo#123` を使う。帰属表記はユーザーの既存方針とリポジトリの要件に従い、必要なクレジットを保持する。新たな帰属は事実に基づくものだけを記載する。

## 依頼の適用

作成・更新が既に依頼されていれば、その範囲の許可を取り直さず適用する。文案だけの依頼ではタイトルと本文案を成果物とする。投稿の許可や対象が実際に不足している場合は、利用可能な情報でレビュー可能な結果を整えてから、不足している点だけを確認する。

新規 PR はユーザーの指定がなければ draft とする。既存 PR のタイトル・本文の更新では draft または ready の状態を保ち、依頼された項目と範囲を編集する。

本文は構造化ツール引数か UTF-8 の一時ファイルで正確に渡す。CLI では、確認済みの対象と作成済みの文面を変数へ設定し、依頼に対応するコマンドを選ぶ。

```bash
gh pr create --repo "$pr_repo" --base "$pr_base" --head "$pr_head" --draft --title "$pr_title" --body-file "$pr_body_file"
```

期待する結果は、指定した base と head の新規 draft PR の URL である。ユーザーが ready を指定した場合は `--draft` を省く。

```bash
gh pr edit "$pr_number" --repo "$pr_repo" --title "$pr_title" --body-file "$pr_body_file"
```

期待する結果は、指定した PR のタイトル・本文が更新され、draft または ready の状態が維持されることである。依頼の対象外の項目は、そのオプションを省く。

PR の URL と実際の適用結果を報告する。書き込み結果が不明なときは再試行前に対象を確認し、作成済み PR の重複を防ぐ。
